# Introduction to Software Engineering

## Overview of Software Engineer
### **SDLC: Software development life cycle**
- Systematic process to develop high quality software
- Aims to produce software that meets requirements
- Defined phases with their own processes and deliverables
- Cycle of planning,design, and development
- Minimizeds development risks and costs

### **Phases of the SDLC**
1. Planning: 
  **Requirnment:**  Gathered, Analyzed, Documented, Prioritized
  **factors to be Consider:** Users, Purpose, Resourcing, Compliance, Inputs/Outputs, Scheduling, Risk ID, QA
  **Prototyping:**
    - Small- scale replica to clarity requirements
    - Test design ideas
    - Can be developed at various stages of the SDLC
  plan will to turn into SRS(software requirement specification)
2. Design
  prototype- design document
3. Development  
4. Testing: Unit, Integration, System, Acceptance  
5. Deployment
  Tested Code or Microservice -> User acceptance testing environemnt -> Production environment
6. Maintenance
  identify Other bugs, User interface issues, New and changing requirements, Code enhancements

### **Building Quality Software - common software engineering processes**
1. **Requirement gathering**
    - The software requiements specification (SRS) encompasses the process of collecting and documenting the set fo requirements that the software needs to adhere to
    - It may include a set of use cases that describe the business need and users flows that the software must implement
    Software requirements can be classificed into four broad categories: Functional, External & user interface, System features, non functional
2. **Design**
    - Tranforming requiremetns into code
    - Breaking down requirements into sets of related components
    - Communicating business rules and application logic
3. **Coding for quality**
    - Maintainability
    - Readability
    - Testability
    - Security
    Quality code must fulfill the intended requirnments of the software without defects
      - Clean and consistent
      - Easy to read and maintian
      - Well documented
      - Efficient
    Coding for quality entails following a set of coding practices during development
      - Following coding standards
      - Using linters to detect errors
      - Commenting in the code itself to make it easy to understand and modify
4. **Testing**
  The process of verifying that the software matches established requirements and is free of bugs
    -  Identify errors, gaps, opr missing requirements
    -  Ensures reliabililty, Security, performance, and efficiency
    levels of testing: 
      - Unit testing
      - Intergration testing
      - system testing
      - User acceptance testing (UAT) or Beta testing
5. **Releases**

    **alpha**
      - Select stakeholders
      - May contian errors
      - Preview of function version
      - Design changes may occur
    
    **beta**
      - All stakeholders
      - User testing 
      - Meets requirements
    
    **ga**(General Availability)
      - Stable 
      - All users

6. **Documenting**
    for technical user & non - techhnical user
    - System documentation: README files, inline comments, architecture and design documents, verification information and maintenance guides
    - User documentation: User guides, instructional videos, manuals, online and inline help    

### Requiement gathering process
**Steps to gathering requirements**:
 - Identifying stakeholders: decision makers, end-users, system adm, eng, marketing, sales, customer support 
 - Establishing goals and objectives: 
    Goal: broad, long-term achievable outcomes
    Objectives: actionable, measurable actions that achieve the goal
   
 - Eliciting requirements from the stakeholders
 - Documenting the requirements
 - Analyzing and comfirming the requirements
 - prioritizing
   - must-have
   - Highly desired
   - Nice to have

**Requirement documentation**
1. **Software requirement specification(SRS) - most common**
 SRS Captures functionalities the software should perform and Establishes benchmarks/ service -levels for performance
 contains
   - Purpose and scope
   - Constraints, assumptions,
   - dependencies
   - Requirements

2. **User Requiement specification(URS)**
   - URS describes business need and end-user expectations
   - User Stories:
     - Who is the user?
     - What is the function that needs to be performed
     - Why does the user want this functionality
   - Confirmed during user acceptance testing
   - often combined into the SRS

3. **System requiement specification(SysRS)**
   - Outlines requirement of the system
   - Broadeer than an SRS
   - Contians:
     - System capabilities
     - Interfaces and user characteristics
     - Policy
     - Regulations
     - Personnel
     - Performance
     - Security
     - System acceptance criteria
     - Harware expactations
