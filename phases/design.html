Design

Translate approved requirements into an implementable system structure: components, interfaces, data, behavior, security boundaries, performance choices, and deployment shape.

Question this phase answers

How will the system satisfy its requirements, and what tradeoffs will guide the people who build it?

At a glance

Design makes implementation decisions visible before code hides them.

Design converts the required behavior and qualities into a coherent plan. It explains what parts the system needs, how those parts communicate, who owns data, how failures are handled, and which decisions protect security, performance, reliability, and maintainability.

InputsApproved requirements

Functional behavior, quality expectations, interfaces, constraints, assumptions, dependencies, and acceptance criteria.

Core workModel and decide

Choose architecture, define boundaries, model behavior and data, specify interfaces, and compare tradeoffs.

OutputsAn implementable design

Design description, architecture and UML diagrams, API contract, data model, security design, and deployment specification.

Design workflow

Move from drivers to decisions

  1. Extract architecture driversIdentify the requirements that strongly shape the system: scale, security, reliability, interoperability, performance, maintainability, cost, and delivery constraints.
  2. Divide responsibilitiesGroup related behavior into modules, components, or services with clear ownership and minimal unnecessary dependency.
  3. Model structure and behaviorUse diagrams to show static organization, runtime states, event-driven changes, and chronological interaction between objects or services.
  4. Define contractsSpecify APIs, user interfaces, data formats, validation rules, failure responses, and the boundaries where systems exchange information.
  5. Design data and deploymentChoose data ownership, persistence, consistency, security controls, environment topology, and the route a production request will follow.
  6. Record tradeoffsExplain why a choice fits the requirements, what it costs, what alternatives were rejected, and which risks must be tested or monitored.

Modeling

Show both organization and behavior

Structured design

Structured design divides a problem into modules and sub-modules. Strong designs aim for high cohesion, so related work stays together, and loose coupling, so a change in one module has limited impact on others.

Behavioral models

Behavioral models show what a system does, how it responds to events, and how objects communicate over time. They describe observable behavior without prescribing every internal implementation detail.

UML: Unified Modeling Language is a programming-language-independent notation. Structural diagrams show organization and relationships; behavioral diagrams show states, events, and interactions.

Architecture approaches

Objects form components; components can form services.

  • Component-based architectureDecomposes an application into reusable, replaceable, extensible, encapsulated units with minimal dependency on one another.
  • Service-oriented architecture (SOA)Packages business capabilities as loosely coupled services that communicate across a network and can be deployed independently.
  • Distributed systemRuns services on different machines and coordinates them through messages, often using HTTP, while presenting one coherent system to the user.
  • Common distributed patternsClient-server, three-tier, peer-to-peer, and microservices organize networked responsibilities in different ways.

Design qualities: resource sharing, fault tolerance, concurrency, scalability, and heterogeneity matter when services run across multiple nodes.

Plain-language terminology

Terms used in Design

Architecture
The high-level structure of a system, including major parts, responsibilities, boundaries, and connections.
Module
A distinct part of the software that groups related responsibilities.
Component
An encapsulated unit of functionality designed to work with other parts of an application.
Service
An independently deployable unit that provides a business capability to clients or other systems.
Encapsulation
Hiding internal data and implementation behind a controlled public interface.
Cohesion
The degree to which responsibilities inside one module belong together; higher cohesion is usually easier to understand.
Coupling
The dependency between modules; loose coupling means a change in one part causes fewer changes elsewhere.
Abstraction
A simplified view that exposes the important behavior while hiding unnecessary internal detail.
UML
Unified Modeling Language, a standard visual notation for representing software structure and behavior.
State transition diagram
A behavioral diagram showing system states, events, and the transitions caused by those events.
Sequence diagram
An interaction diagram showing communication between objects or services in chronological order.
API
An application programming interface: a defined contract for requesting data or behavior from another software component.
SOA
Service-oriented architecture: a system organized around loosely coupled networked services.
Node
A network-connected device that can recognize, process, and transmit data and may run one or more services.
Fault tolerance
The ability to keep operating when a node, service, or component fails.
Scalability
The ability to handle increased users or work by adding or improving resources.
