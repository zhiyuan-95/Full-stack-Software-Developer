Phase 06 · Support and learning

Maintenance

Support and improve the deployed product by correcting production defects, addressing usability problems, keeping documentation accurate, and turning feedback into the next planning cycle.

Question this phase answers

What is the live system teaching us, what must be corrected now, and what should become planned work next?

At a glance

Maintenance makes production part of the lifecycle.

Deployment is not the end of software development. Real users, traffic, failures, security findings, support requests, and changing needs reveal information that no pre-production environment can fully reproduce.

InputsProduction signals

Monitoring, incidents, support cases, security findings, user behavior, feedback, defects, and new constraints.

Core workRestore, correct, learn

Triage impact, stabilize service, find root cause, implement a safe change, retest, release, and update guidance.

OutputsA safer system and new priorities

Incident record, patch, regression evidence, updated runbook and user docs, and a prioritized improvement backlog.

Maintenance workflow

Operate the service and close the learning loop

  1. Observe health and useMonitor availability, errors, security, performance, capacity, user behavior, and support demand.
  2. Triage the signalDetermine impact, urgency, affected users, workaround, owner, and whether the situation is an incident, defect, request, or planned enhancement.
  3. Stabilize serviceFollow the runbook to restore safe operation, limit harm, communicate status, and preserve evidence needed for diagnosis.
  4. Find the root causeIdentify the underlying system or process condition that allowed the problem, not only the visible symptom.
  5. Correct and verifyImplement the smallest safe change, repeat relevant tests, deploy under control, and confirm that the correction does not create a regression.
  6. Update and prioritizeSynchronize documentation and turn incidents, feedback, defects, and ideas into an ordered backlog for Planning.

Documentation maintenance

The guide must match the product users actually have.

Software documentation can be written, graphical, or video-based and may serve end users, developers, QA engineers, administrators, and other stakeholders. Whenever behavior changes, the relevant guidance and evidence should change with it.

  • Requirements and designUpdate expectations and models when a correction or enhancement changes approved behavior, interfaces, architecture, or constraints.
  • Technical documentationKeep code comments, README files, API references, engineering notes, and maintenance guidance aligned with the implementation.
  • QA documentationAdd or revise test cases, regression coverage, defect history, test reports, and requirement traceability.
  • User documentationRevise guides, FAQs, tutorials, online help, and manuals when the interface or operating procedure changes.
  • Process documentationUpdate runbooks and standard operating procedures when the organization learns a safer or more reliable way to act.

Feedback loop

Maintenance ends by creating Planning inputs.

Immediate work

Restore service, protect users and data, fix production defects, address user-interface problems, correct documentation, and reduce the chance of recurrence.

Next-cycle work

Convert feedback, incidents, changing requirements, capacity needs, security findings, and enhancement ideas into prioritized backlog items with evidence and owners.

The loop is intentional: production learning changes the understanding of the problem. That learning returns to Planning, where scope, requirements, priorities, and risks can be reconsidered.

Evidence and cycle handoff

What Planning should receive next

EvidenceWhat it supports
Monitoring and service dashboardShows availability, performance, errors, capacity, and user-impact trends over time.

Patch and regression resultsDemonstrate that the correction works and important existing behavior still passes.

Traceability closes the loop

Operational evidence returns to stakeholder needs and the next iteration rather than disappearing after a patch.

Plain-language terminology

Terms used in Maintenance

Monitoring
Continuously observing a system’s health and behavior so changes and failures can be detected.
Telemetry
Data emitted by a running system to describe its operation and use.
Log
A time-ordered record of events and messages produced by software or infrastructure.
Metric
A numeric measurement tracked over time, such as error rate, latency, or request volume.
Trace
A record that follows one request or operation across multiple components or services.
Incident
An event that disrupts or degrades a service and requires a coordinated response.
Triage
Classifying incoming problems by impact, urgency, affected users, and required response.
Root cause
The underlying condition that allowed a problem to occur, beyond the visible symptom.
Patch
A focused software change released to correct a defect or vulnerability.
Runbook
Step-by-step operational guidance for responding to a known situation or performing a routine action.
Service objective
A measurable target for service behavior, such as availability, response time, or recovery time.
Backlog
An ordered list of defects, improvements, requests, and planned work.
Regression
An existing behavior that stops working because of a later change.
Corrective action
A change intended to remove the cause of a detected problem.
Preventive action
A change intended to reduce the chance that a similar problem will occur in the future.
