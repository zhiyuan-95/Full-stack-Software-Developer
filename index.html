Lifecycle-wide segment 01

Documentation keeps the work understandable.

Documentation is not a seventh phase. It is evidence and guidance created throughout the lifecycle, then kept synchronized with the software during maintenance.

Product and process documentation

Product documentation explains the software, its design, behavior, operation, and use. Process documentation explains how people should complete a task or business process.

  • Requirements documentationDefines expected features, behavior, constraints, interfaces, and acceptance expectations. Common examples are an SRS, SysRS, and URS.
  • Design documentationExplains how architecture, components, data, interfaces, and deployment choices will satisfy the requirements.
  • Technical documentationHelps developers understand and maintain the implementation through code comments, README files, API references, and engineering notes.
  • Quality assurance documentationRecords the test strategy, cases, data, results, defects, metrics, and traceability between requirements and evidence.
  • User documentationHelps end users install, operate, and troubleshoot the product through guides, tutorials, help content, and manuals.
  • Standard operating procedure (SOP)Provides the exact organization-specific steps for a repeated, complex task, such as reviewing and merging code into the main branch.

Lifecycle-wide segment 02

Methodology changes the cadence, not the vocabulary.

A methodology is the operating pattern a team uses to organize lifecycle work. Waterfall and V-Shape move sequentially; Agile repeats the same kinds of work in short cycles.

MethodFlowTestingFeedbackBest fitMain tradeoff
WaterfallSequential: one phase completes before the next begins.Usually concentrated later in development.Substantial customer feedback arrives late.Stable requirements and a strong need for upfront estimates.Easy to understand and plan, but costly to change late.
V-ShapeSequential: verification work is paired with validation work.Planned early and executed against its paired design level.Structured checkpoints, but limited late flexibility.Stable, highly structured projects where test planning must start early.Clear evidence pairing, but even more rigid than Waterfall.
AgileIterative: planning, design, development, and testing repeat in sprints.Continuous inside each sprint.Frequent demos and stakeholder feedback.Changing requirements and incremental delivery.Adapts quickly, but long-range budget and schedule estimates are harder.

V-Shape language

Verification asks whether the team designed and built the product correctly. Validation asks whether the completed behavior satisfies the user and business need. Each design level is paired with a corresponding test level.

Agile language

A sprint is a short development cycle, usually one to four weeks. A sprint demo shows working functionality. A minimum viable product (MVP) contains enough core functionality to test the product idea and gather useful feedback.

Plain-language reference

Terminology index

Specialized terms used across the guide are defined here. Each phase page also repeats the terms needed to understand that phase without returning to this page.

36 terms
Acceptance criteria
Observable conditions that must be true for a requirement or feature to be accepted.
Agile
An iterative approach that delivers working software in short cycles and uses frequent feedback to adjust future work.
API
An application programming interface: a defined way for software components or services to request data or behavior from one another.
Application environment
The hardware, operating system, network, libraries, configuration, and other resources needed to run an application.
Architecture
The high-level structure of a system, including its major parts, responsibilities, boundaries, and connections.
Artifact
A work product created during development, such as a requirement, diagram, source file, test result, build, or runbook.
Assumption
A condition expected to be true for planning purposes but not yet proven.
Backlog
An ordered list of work, defects, improvements, and requirements that a team may address.
Component
An encapsulated unit of functionality that collaborates with other parts of an application.
Constraint
A limit that narrows available choices, such as a law, platform, deadline, budget, or security rule.
Dependency
Another system, library, service, team, or condition that the software relies on.
Deployment
The controlled process of releasing software and its configuration into an environment where it can run.
Distributed system
A system whose services run on different networked machines while appearing to users as one coherent product.
Exit signal
The evidence that a phase has done enough work for the next phase to proceed responsibly; often called an exit gate.
Functional requirement
A statement of what the software must do, such as calculate a result or allow a user to complete a task.
Iteration
One pass through a repeated cycle of planning, building, checking, and learning.
Maintainability
How easily software can be understood, corrected, adapted, and improved.
Methodology
A structured approach for organizing how a team plans, communicates, builds, tests, releases, and responds to feedback.
Module
A distinct part of a software system that groups related responsibilities.
Nonfunctional requirement
A quality or operating expectation, such as security, performance, reliability, accessibility, or scalability.
Prototype
A preliminary model used to test an idea, clarify an uncertain requirement, or collect early feedback.
Quality assurance (QA)
Planned work used to prevent, find, record, and resolve quality problems.
Regression testing
Rechecking existing behavior after a change to find accidental breakage.
Requirement
A documented need, behavior, interface, constraint, or quality expectation the system must satisfy.
SDLC
The Software Development Life Cycle: the connected phases used to plan, design, build, test, release, and maintain software.
Service
An independently deployable unit that provides a business capability to clients or other systems.
Software stack
The combined languages, frameworks, libraries, runtime, data tools, and infrastructure used to build and run software.
Sprint
A short Agile cycle in which a team plans, builds, tests, and demonstrates a small increment of working software.
Stakeholder
A person or group that uses, funds, builds, operates, approves, sells, supports, or is affected by the software.
System Under Test (SUT)
The application, service, feature, module, or complete system currently being tested.
Traceability matrix
A table that connects requirements to the design, implementation, and test evidence that satisfy or verify them.
UAT
User acceptance testing: formal testing by users or stakeholders to decide whether the software meets their needs.
UML
Unified Modeling Language: a standard visual notation for representing software structure and behavior.
URS
User Requirements Specification: a description of business needs and end-user expectations.
SRS
Software Requirements Specification: a detailed description of the software’s required behavior, interfaces, constraints, and qualities.
SysRS
System Requirements Specification: requirements for the full system, including software, hardware, policies, people, and interfaces.
