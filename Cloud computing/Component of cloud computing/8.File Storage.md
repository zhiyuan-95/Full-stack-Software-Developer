# Cloud File Storage

## Summary

**File Storage** is remote, provider-managed storage that must be mounted to a compute node before applications can use it. It is presented as a shared drive and can generally be mounted by multiple compute nodes simultaneously.

Compared with Direct Attached Storage, File Storage can provide greater capacity, better resilience, less user-managed disk maintenance, and shared access. Its principal tradeoff is that performance depends on both the underlying disks and the Ethernet network connecting the storage to compute nodes.

## Architecture

```text
Provider-managed storage appliance
             │
     Dedicated Ethernet network
             │
   ┌─────────┼─────────┐
   ↓         ↓         ↓
Compute 1  Compute 2  Compute 3
```

The physical disks are housed in a specialized remote storage appliance rather than inside the compute server. The cloud provider manages the appliance and its underlying infrastructure.

The lecture describes these appliances as offering:

- Resilience against hardware failure
- Larger storage capacities
- Reduced disk-management responsibilities for customers
- Security capabilities such as encryption in transit

Exact resilience and security capabilities depend on the provider and storage service.

## File-storage terminology

The lecture uses several related terms:

- **File Storage**
- **Network Attached Storage (NAS)**
- **Network File Storage**
- **Network File System (NFS)**

Technically, **NAS** describes network-connected file-storage architecture, while **NFS** is a protocol commonly used to present shared files to compute nodes.

## File Storage versus Direct Attached Storage

| Characteristic | File Storage | Direct Attached Storage |
|---|---|---|
| Physical location | Remote storage appliance | Inside or near the compute host |
| Connection | Ethernet network | Direct or local connection |
| Sharing | Can typically be mounted by multiple nodes | Usually limited to one node |
| Capacity | Can support larger provisioned volumes | Limited by local hardware |
| Performance | May vary with network load | Generally faster and more predictable |
| Resilience | Provider-managed storage appliances offer greater resilience | Typically less resilient |
| Management | Provider handles the storage appliance | More disk management may fall to the user |
| Cost | Can be less expensive | Often more expensive |
| Common use | Shared files and repositories | Operating systems and fast local data |

## Network-performance tradeoff

File Storage connects to compute nodes through an Ethernet network, commonly a dedicated storage network.

Even when providers design these networks for high traffic volumes, performance may vary because:

- Other traffic can load the network.
- Available bandwidth can change.
- Consistently high network speed is not guaranteed.

File Storage is therefore best suited to workloads that can tolerate some network-performance variation.

## Common use cases

Because the same File Storage volume can be mounted by multiple compute nodes, it works well for shared-data workloads such as:

- Departmental file shares
- Landing zones for incoming files
- Shared application-processing directories
- File repositories used by web services
- Workloads requiring a common hierarchical file structure

File Storage can also support databases when cost is the main concern, but the lecture identifies storage and network speed as an important tradeoff.

## IOPS

**IOPS** means **Input/Output Operations Per Second**. It measures how many disk read or write operations the underlying storage can perform each second.

IOPS does **not** measure the speed of the network between the storage appliance and the compute node.

```text
Application performance
        │
        ├── Storage performance: IOPS
        └── Network performance: bandwidth and network load
```

### IOPS sizing tradeoff

| IOPS selection | Result |
|---|---|
| Too low | Storage can become a bottleneck and slow the application |
| Appropriate | Workload receives the required performance at a reasonable cost |
| Too high | Customer may pay for performance the application does not use |

Higher IOPS capacity normally costs more.

## IOPS example

The lecture gives an example in which:

- A file share is mounted on **30 compute nodes**.
- The application performs **60 total storage operations per minute**.

The average operation rate is:

```text
60 operations ÷ 60 seconds = 1 IOPS
```

The number of mounted nodes alone does not determine the IOPS requirement. Sizing depends on the total number and pattern of read/write operations produced by the applications.

## Selection guidance

File Storage is a strong choice when:

- Multiple servers must access the same data.
- A familiar folder-and-file structure is required.
- The workload can tolerate some variation in network performance.
- Provider-managed resilience and maintenance are valuable.
- Cost is more important than consistently high disk and network speed.

It is less suitable when an application requires highly consistent, low-latency storage performance; Block Storage may be more appropriate for those workloads.

## Key takeaway

File Storage provides scalable, provider-managed, shared storage over a network. Its main advantage is that several compute nodes can use the same files and directories. Its main tradeoff is variable network performance, so both **IOPS capacity** and network behavior must be considered when sizing it for an application.
