# Block Storage and File Storage

## Summary

**Block Storage** divides data into fixed-size chunks called blocks and stores each block under a unique address. It is mounted to a compute node as a volume and is designed for applications requiring consistent, low-latency disk performance.

**File Storage** presents data through a shared file-and-folder structure. It can generally be mounted by multiple compute nodes, making it better suited to shared files, collaborative work, and applications that do not require consistently high storage performance.

## Block Storage architecture

```text
Compute node
     │
Storage Area Network (SAN)
     │
Block-storage volume
├── Block 1: unique address
├── Block 2: unique address
└── Block 3: unique address
```

The operating system sees the mounted volume as another disk. The server or application is responsible for organizing the raw blocks through a file system or another storage structure.

## Block Storage characteristics

Block Storage:

- Must be attached to a compute node before use
- Is provisioned as a volume
- Is commonly accessed through a **Storage Area Network (SAN)**
- Provides fast and consistent read/write performance
- Supports workloads requiring low latency or high IOPS
- Is normally mounted to one compute node at a time
- Can often be resized or assigned different IOPS characteristics
- Is typically more expensive than File Storage
- Is managed through provider-maintained storage appliances

The lecture describes Block Storage as using a dedicated high-speed fibre-optic network. Actual cloud-storage transport technologies and attachment capabilities vary by provider.

## Resilience and security

Provider-managed Block and File Storage commonly include:

- High availability
- Redundant storage
- Protection against individual disk or volume-component failures
- Encryption in transit
- Encryption at rest

The second lecture segment describes Block Storage as storing redundant data across the volume so that a disk failure can be handled without affecting the application. The exact redundancy and recovery guarantees depend on the provider and service tier.

## Block Storage use cases

Block Storage is appropriate for applications requiring consistently fast disk access, including:

- Transactional databases
- Relational databases
- Mail servers
- VMware boot volumes
- High-performance applications
- Workloads requiring large numbers of IOPS

It is less suitable when several compute nodes must share the same mounted storage.

## File Storage architecture

```text
Server A ──┐
Server B ──┼── Ethernet network ── Shared file system
Server C ──┘                       ├── Folders
                                  └── Files
```

File Storage is commonly presented through network-attached file protocols such as **NFS**. Multiple servers or runtimes can access the same file share.

## File Storage characteristics

File Storage:

- Is attached through an Ethernet network
- Presents data through files and directories
- Can be mounted by multiple compute nodes
- Supports shared access
- Is highly scalable
- Is generally less expensive than Block Storage
- May experience variable network performance as traffic load changes
- Is suitable when consistently low latency is not required

The lecture states that a file share may support **80 or more compute nodes**, but the actual limit depends on the provider and service.

Concurrent reads and writes are possible, although conflict handling depends on the file system, locking behavior, and application design.

## File Storage use cases

File Storage is appropriate for:

- Departmental or organizational file shares
- Collaborative workspaces
- Web-hosting environments
- Mixed text and media files
- Shared repositories
- Workloads requiring several servers to access the same files
- Applications where cost matters more than consistently low latency

## Block versus File Storage

| Characteristic | Block Storage | File Storage |
|---|---|---|
| Data organization | Raw, uniquely addressed blocks | Files and hierarchical folders |
| Presentation | Disk-like volume | Shared file system |
| Common connection | SAN or high-speed storage network | Ethernet network |
| Attachment | Normally one compute node | Multiple compute nodes |
| Performance | Fast and consistent | May vary with network load |
| Latency | Designed for low latency | Generally higher or more variable |
| IOPS | Suitable for high-IOPS workloads | Configurable, but commonly lower |
| Cost | Generally higher | Generally lower |
| Sharing | Not normally intended for shared mounting | Designed for shared access |
| Typical workloads | Databases, mail servers, boot volumes | File shares, collaboration, web content |
| Management | Provider-managed appliance | Provider-managed appliance |
| Security | Often encryption at rest and in transit | Often encryption at rest and in transit |

## IOPS considerations

**IOPS** means **Input/Output Operations Per Second**. It measures the number of storage read and write operations that can be completed each second.

Both File and Block Storage require appropriate IOPS sizing:

- Too few IOPS can create an application bottleneck.
- Too many IOPS may increase cost unnecessarily.
- Some providers allow IOPS to be adjusted when application requirements change.

Applications with transactional activity or consistently high disk demand generally benefit from Block Storage. Shared-file workloads with moderate performance requirements often fit File Storage.

## Choosing between them

```text
Does more than one compute node need the same mounted storage?
├── Yes → Consider File Storage
└── No
    └── Does the workload need consistently low latency or high IOPS?
        ├── Yes → Consider Block Storage
        └── No → Compare cost, sharing, and performance requirements
```

Choose **Block Storage** for consistent performance, low latency, databases, or boot volumes.

Choose **File Storage** for shared access, collaboration, familiar file structures, or lower-cost network storage.

## Key takeaway

Block and File Storage are both traditional, provider-managed storage models that remain useful on premises and in the cloud. Block Storage prioritizes consistent, high-performance disk access for one compute node, while File Storage prioritizes shared access and familiar file organization across multiple nodes.
